# Current-State Review — ai-marketing-suite baseline (2026-08-19)

Reviewed at import commit `6db77fe` (= `ai-marketing-suite@a65f48e`). Verified
empirically on this machine: offline demo runs **19/19 agents valid**, test suite
**207/207 passing** (0.39s, fully offline).

## Verdict

The **product core is real and well-engineered**: a clean 6-layer/19-agent DAG with a
disciplined agent contract (versioned prompt asset + JSON Schema + ~40 lines of
contract code), schema-skeleton injection to prevent output drift, a fixture provider
that makes the whole suite runnable offline, and a platform-neutral export bundle.
The **production shell around it is scaffold, not product**: deploy assets are
incomplete and in one place actually broken, there is no UI, no IaC, no observability,
and Layer 4/5 "integrations" are prompt-engineering only.

## Gaps and defects (fix or replace)

1. **DB password wiring bug** — `deploy/cloudbuild.yaml` mounts the secret as env
   `SQL_APP_PASSWORD`, but `suite/infra/clients.py::_pg_pool()` builds its conninfo
   with no password and reads no env var; it relies on `PGPASSWORD`, which only
   `suite/scripts/run_live.sh` sets. A Cloud Run Job from this image cannot
   authenticate to Cloud SQL. (Moot once persistence moves to Firestore.)
2. **Cloud Workflows choreography incomplete** — `deploy/workflows/suite-pipeline.yaml`
   encodes only L1–L2; `await_gate` is a 30s-interval sleep loop with a TODO, no
   Firestore check. The human-gate wait was never implemented.
3. **No review UI** — docs reference a "Firebase review UI" that does not exist in any
   repo. The human gate has no surface. (This is what the Django app becomes.)
4. **Layer 4/5 are spec-only** — agents 4.2/4.4/5.1/5.2/5.3 emit generation specs for
   fal.ai / Meta / Google / TikTok / Ayrshare / Resend / Twilio / HubSpot, but no
   client code for any of those vendors exists; MCP `platform_apis` domain raises
   `NotImplementedError`.
5. **Split-brain persistence** — Cloud SQL (`client_profiles`, `memory_blocks`;
   migration 002 marked "pending apply", never confirmed run) + Firestore (review
   queue only). `client_embeddings` (pgvector, HNSW) has zero writer code and a known
   1536-vs-768 dimension mismatch left unresolved.
6. **Prod-by-default config** — `suite/infra/config.py` defaults to
   `SUITE_LLM_PROVIDER=vertex`, `SUITE_BACKEND=gcp`; a bare import with no env tries
   to reach real GCP.
7. **No observability** — no `logging` usage in core code, no tracing, no metrics, no
   cost capture (despite a cost model referenced in every docstring). Retry logic is a
   single blind re-ask on schema failure; transport errors are not retried at all
   (`base.py` catches broadly and returns a failed result).
8. **Client-data leakage** — `suite/inputs/alonso-y-cia.json` carries real Alonso y
   Cía business data (segments, confirmed MXN 50,000/mo budget) inside the "generic
   product engine" repo.
9. **Stale build tooling** — `workflows/build-*.js` hardcode an absolute Google Drive
   path from the original AcmeCo pilot and reference spec docs
   (`project/specs/ARCHITECTURE.md`, `AGENT_COST_MODEL.md`, phase docs) that were
   never migrated into this repo — the human-readable spec layer is missing here.
10. **Dependency drift** — `pydantic`, `python-dotenv`, `google-cloud-secret-manager`,
    `google-cloud-aiplatform`, `pytest-asyncio` declared but unused by any Python
    code; `requires-python >= 3.11` vs the 3.12 used everywhere; pyproject comment
    claims unix-socket Cloud SQL access while the code does TCP-proxy.
11. **Dead config** — `TOPIC_REVIEW` (`review-queue-events`) is never published to.
12. **Model IDs are last-gen** — Claude Sonnet 4.6 / Haiku 4.5 / Opus 4.7 on Vertex;
    the target stack (Gemini 3.x via `google-genai`) replaces this entirely.
